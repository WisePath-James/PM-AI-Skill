# 02 - Human Owner 需求访谈与澄清

## 目的

需求访谈是将 Human Owner 的原始想法转化为结构化、可跟踪、可验收的需求的关键步骤。本文件提供访谈模板和澄清清单。

## 访谈前准备

在开始访谈前，先确认：
1. 已执行 Memory Boot（读取项目已有记忆）
2. 已理解项目背景和上下文
3. 准备好访谈目标和问题清单

## 访谈模板

### 开场

```
您好，我来确认一下项目的核心目标。
请用一两句话告诉我：这个项目最终要交付什么？
```

### 核心问题清单

#### 1. 目标澄清
- 这个系统/功能的核心用途是什么？
- 谁能用？在哪里用？
- 怎么判断项目成功了？

#### 2. 范围边界
- 这个版本必须包含什么？（MVP）
- 这个版本**不**包含什么？
- 有没有类似的现有系统需要对接或避免重复？

#### 3. 质量标准
- 性能/响应时间有要求吗？
- 需要支持哪些浏览器/设备/平台？
- 有安全或合规要求吗？
- 验收由谁来做？标准是什么？

#### 4. 约束条件
- 预算范围？
- 时间限制？
- 技术限制（禁止使用的技术、特定环境）？
- 谁能提供资源（API key、账号、文档）？

#### 5. 优先级
- 如果只能做一个功能，是哪个？
- 如果只能做两个功能，是哪两个？
- 有没有必须在上线的当天就工作的功能？

#### 6. 风险与假设
- 你认为最大的风险是什么？
- 有哪些事情你觉得可能会出问题？
- 我们假设了什么前提条件？

## 验收标准确认（必须获取）

每个需求必须有对应的验收标准。格式：

```
需求：[描述]
验收标准：
- [具体可验证的标准 1]
- [具体可验证的标准 2]
- 验收人：[谁来做最终验收]
```

**无效的验收标准示例**：
- "系统要快" → 无法验证
- "界面要好看" → 主观标准

**有效的验收标准示例**：
- "API 响应时间 P95 < 200ms（基于 1000 次连续请求测试）"
- "登录页面通过 WCAG 2.1 AA 无障碍审计"
- "用户输入无效邮箱时，3 秒内在表单下方显示红色错误提示"

## 需求分类

Human Owner 的需求可能以多种形式出现：

| 输入形式 | PM AI 处理方式 |
|---------|---------------|
| 功能描述（模糊） | 澄清 + 拆解为具体需求 |
| 错误报告/投诉 | 记录为 Issue，评估是否属于范围 |
| 竞品参考（"像 XX 那样做"） | 分析核心需求 vs 表面模仿，分离真实需求 |
| 技术方案（"用 XX 技术做"） | 记录为技术约束，评估合理性 |
| 变更请求 | 进入变更控制流程 |
| 模糊想法/灵感 | 先记录为 Backlog Item，不立即承诺 |

## 澄清后的行动

1. 将需求写入 REQUIREMENTS_REGISTER.md
2. 评估是否需要更新范围基线
3. 如涉及重大变更，发起变更控制流程
4. 向 Human Owner 确认理解是否正确

## 快速澄清问题集（现场使用）

当 Human Owner 说了一句模糊的需求描述时，立即追问：

- "你说的『快速』具体是多快？给我们一个数字。"
- "『支持所有用户』——预计有多少用户？同时在线最多多少人？"
- "『安全』——具体指防止未授权访问，还是数据加密，还是两者？"
- "这个功能如果不做，对项目有什么影响？"
- "这个功能如果现在不做，放到下一个版本可以吗？"

## New Project Vague Intake / 新项目模糊输入首轮问题

当 Human Owner 提供模糊宏观想法（如"我想做一个 XX app"）而没有具体范围时，使用以下问题集进行首轮 intake。问题数量控制在 8-10 个，不要扩展为长问卷。

> **语言规则**：使用 stakeholder 的主要工作语言提问和记录。文件路径、命令、API path、error code 等可保留英文原文。

### 必问的 9 个问题

**1. 项目一句话目标**
"请用一句话告诉我：这个项目最终要交付什么、解决什么问题？"

**2. 目标用户**
"这个系统谁会用？在什么场景下用？"

**3. MVP 必须包含什么**
"如果第一个版本只能交付 1-3 个功能，你认为哪 1-3 个是绝对必要的？"

**4. 明确不做什么**
"第一个版本**不做**什么？（比如：不需要登录、不需要数据导出、不需要多用户等）"

**5. 成功 / 可用标准**
"你怎么判断第一个版本是可用的/成功的？有没有可验证的标准？"

**6. 主要约束**
"有没有时间限制？平台要求（浏览器/设备/操作系统）？技术限制（不能用某技术）？需要对接的外部账号或 API？"

**7. 数据 / 安全需求**
"有没有需要存储的用户数据？有没有安全或合规要求（如隐私政策、GDPR、数据本地化）？"

**8. 主要风险或不确定性**
"你觉得这个项目最大的风险或不确定性是什么？有没有你还没想清楚的地方？"

**9. 第一阶段 / 第一个里程碑**
"第一个可演示的版本包含哪些功能？预计什么时候可以演示？"

### Intake 后规则

- 不得在获取以上信息前创建 WBS。
- 不得在获取以上信息前发给 Coder 工作包。
- 汇总所有答案，起草 `PM_PROJECT_BRIEF.md` 草案。
- 将草案发给 Human Owner 确认。
- Human Owner 确认后才可建立 Scope Baseline、WBS 或发给 Coder 工作包。
