# 06 - 混合交付策略

## 交付模式选择器

根据项目特征，从以下模式中选择主交付模式。模式不是固定的，可以根据项目进展切换。

### 模式对比矩阵

| 维度 | 瀑布 | 敏捷 | 混合 | PRINCE2 |
|------|------|------|------|---------|
| 范围确定性 | 高（需求冻结） | 低（持续演化） | 中 | 高 |
| 变更频率 | 低 | 高 | 中 | 可控 |
| 交付节奏 | 阶段末 | 每迭代（1-4周） | 阶段内迭代 | 按阶段 |
| 控制粒度 | 粗粒度（阶段） | 细粒度（迭代） | 双层 | 阶段+例外 |
| 适用场景 | 稳定需求、强合规 | 创新/探索、快速验证 | 主体稳定+局部变化 | 复杂项目、多团队 |
| 阶段门禁 | 阶段末评审 | Sprint Review | 阶段末+迭代末 | 正式阶段评审 |
| 治理强度 | 中 | 低 | 中高 | 高 |

## 各模式核心特征

### 瀑布（Waterfall）
- 阶段：启动 → 规划 → 执行 → 监控 → 收尾（线性顺序）
- 变更：严格变更控制，少量变更可接受
- 适合：需求稳定、监管严格、合同驱动
- 典型场景：合规软件交付、基础设施项目、合同开发

### 敏捷（Agile）
- 迭代节奏：1-4 周固定长度 Sprint
- 角色：Human Owner（Product Owner 授权保留）/ Scrum Master（PM AI）/ Team（Coder）
- 仪式：Sprint Planning → Daily Standup → Review → Retrospective
- 适合：需求不确定、需快速验证、技术创新
- 典型场景：MVP 开发、产品迭代、功能实验

**敏捷中的 PM AI 职责**：
- 作为 Backlog Manager / Delivery Coordinator / Scrum-aware PM
- Sprint Planning 时将已批准的 Backlog Item 转化为 Sprint Goal
- 每个 Sprint 结束时进行 Review + Retrospective
- 保护 Coder 不受频繁需求变更冲击
- **不**作为 Product Owner：最终业务优先级决策由 Human Owner 保留
- 可**推荐**优先级，但**不**能做最终的业务优先级决策

### 混合（Hybrid）
- 外层：瀑布阶段框架（如：Phase 1 基础架构 → Phase 2 功能开发 → Phase 3 集成测试）
- 内层：每个阶段内部采用敏捷迭代
- 适合：主体需求稳定但局部需要快速响应
- 典型场景：企业应用现代化、产品线扩展

### PRINCE2
- 阶段治理：按阶段计划、控制、评审、授权
- 例外管理：设定容差（Tolerance），在容差内授权团队，超出则上报
- 角色：Executive（Human Owner）/Senior User/Senior Supplier/PM
- 适合：复杂项目、多组织参与、多团队协调、需要强治理
- 典型场景：大型系统集成、政府/金融项目、跨部门项目

**PRINCE2 关键控制点**：
- 阶段末评审（Stage End Assessment）：当前阶段是否完成？下一阶段是否授权？
- 例外情况上报：当预测超出容差时，立即上报决策层
- 商业论证持续检查：每个阶段前验证项目是否仍值得继续

### PMBOK 过程组
- 覆盖：启动、规划、执行、监控、收尾全生命周期
- 过程组间关系：监控贯穿全程；规划可能反复；收尾在最后
- 适合：需要全面覆盖知识领域的正式项目管理
- 典型场景：PMP 框架下的项目交付、需要完整文档的项目

### 探索/Spike
- 特征：固定时间（如 1 周）、探索未知技术或验证可行性
- 结果：要么得到明确结论（可行/不可行+原因），要么缩小范围继续探索
- 适合：技术不确定性高、无法估量的场景
- 决策门禁：探索结束后必须有明确结论或下一步计划

### 维护/缺陷修复
- 特征：范围稳定、持续小改进、变更优先于新功能
- 变更控制：每个变更必须评估影响
- 适合：已有系统在生产环境运行
- 关键指标：MTTR（平均修复时间）、可用性

### 紧急/热修复
- 特征：P0/P1 问题，要求立即响应
- 流程：立即修复 → 通知 Human Owner → 事后补文档 + 变更单
- 适合：生产环境故障、安全漏洞
- 注意：跳过常规流程是例外，事后必须补齐

## 模式切换控制

模式切换是重大决策，必须通过变更控制流程。

### 触发条件（需要评估是否切换模式）

- 需求变更频率超过当前模式容纳能力
- 项目规模或复杂度发生重大变化
- Human Owner 要求
- PM AI 评估后建议

### 切换评估清单

```
1. 原因：为什么要切换？
2. 影响：切换对当前进度、已完成工作、团队的影响是什么？
3. 决策：Human Owner 是否批准？
4. 更新：需要更新哪些文档？
   - [ ] 交付策略文档
   - [ ] 项目章程
   - [ ] WBS
   - [ ] 需求登记册
   - [ ] 其他
5. 过渡期：切换期间如何处理正在执行的工作包？
```

### 切换记录格式

```markdown
## 模式切换记录

- 日期：[日期]
- 切换原因：[原因]
- 从：[原模式] → 到：[新模式]
- 影响评估：[影响]
- 批准人：[Human Owner]
- 更新文档：[列表]
```

## 高频需求变化的接收与控制（vibe coding 场景）

在 vibe coding 模式下，Human Owner 可能会频繁提出新想法。

处理方式：
1. **接收**：所有需求都记录到 Backlog
2. **分类**：评估是 P0/P1/P2/P3
3. **控制**：P0/P1 需要 Human Owner 明确确认后才能开始
4. **Backlog 管理**：定期和 Human Owner 一起 review backlog，清理和重排
5. **变化管理**：每 10 个新增需求做一次累积影响评估
